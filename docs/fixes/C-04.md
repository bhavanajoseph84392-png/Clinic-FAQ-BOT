# C-04: Session Insert Outside Tenant Context

## What was wrong

`create_session` in `app/chat.py` inserted a new patient session through `get_db()`. That helper yields a connection without setting `app.clinic_id`, while `patient_sessions` has row-level security enabled and forced with a policy that requires `app.clinic_id` to match the row's `clinic_id`. The insert was therefore rejected by RLS or was not scoped to the clinic.

## Code evidence

Before the change, `app/chat.py:27-33`:

```python
    with get_db() as conn:
        with conn.cursor() as cur:
            cur.execute("""
                INSERT INTO patient_sessions (clinic_id, name, email, token_hash, expires_at)
                VALUES (%s, %s, %s, %s, %s)
                RETURNING id;
            """, (clinic["id"], name, email, token_hash, expires_at))
```

## What changed

The insert now runs inside the tenant transaction used by the other tenant-scoped queries:

```python
    with tenant_tx(clinic["id"]) as conn:
        with conn.cursor() as cur:
            cur.execute("""
                INSERT INTO patient_sessions (clinic_id, name, email, token_hash, expires_at)
                VALUES (%s, %s, %s, %s, %s)
                RETURNING id;
            """, (clinic["id"], name, email, token_hash, expires_at))
```

The SQL, parameters, cookie handling, and redirect behavior are unchanged. The unused `get_db` import was removed.

`tests/test_chat_tenant.py` uses a fake pool and cursor, patches `app.db.get_pool` and `resolve_clinic_by_slug`, and asserts that `set_config` runs first on the connection followed by the `patient_sessions` insert with the same clinic id. No database connection is used.
